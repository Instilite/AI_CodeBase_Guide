A0.3 Stale .indexing Marker Rule (CB-2 fix)

A3.2 ZIP Safety Rules
	•	Compressed size > 15 MB: reject 413 immediately.
	•	Before extraction: sum ZipInfo uncompressed sizes. If > 200 MB: reject 413.
	•	Zip-slip protection: deny absolute paths, deny .. segments, deny weird drive prefixes. Construct safe destination path, verify it stays inside temp dir.
	•	Extract to ./tmp/{job_id}/. After extraction, verify total on-disk bytes <= 200 MB. Then move filtered files to ./repos/{repo_id}/.

A3.3 File Filtering
	•	Keep extensions: .py .js .ts .tsx .jsx .css .html .md .go .java .rb .rs .cpp .c .h
	•	Skip directories anywhere in path: .git node_modules dist build __pycache__ .venv venv
	•	Skip binaries: if first 8 KB of file contains NUL byte, skip.

A3.4 Chunking
	•	Split each file into chunks of 100 lines with 20-line overlap.
	•	Chunk metadata: repo_id, file_path (relative to repo root), start_line, end_line, chunk_index (0..n-1), sha1(text)[:8].

A3.5 Embedding and Chroma Storage
	•	Model: text-embedding-3-small. Batch size: 64 chunks per request.
	•	Collection creation (REQUIRED — CB-4 fix):
collection = client.get_or_create_collection(
    name=f"repo_{repo_id}",
    metadata={"hnsw:space": "cosine"}  # REQUIRED: enables sim = 1-d formula
)
	•	Chunk IDs: f"{file_path}:{chunk_index}:{sha1[:8]}"
	•	Upsert: ids, documents (chunk text), metadatas (file_path, start_line, end_line, chunk_index, repo_id), embeddings.
	•	After restart: PersistentClient must see same collection and queries must work.

A3.6 Background Job Lifecycle
At indexing start:
	•	Create ./repos/{repo_id}/.indexing
	•	Write ./jobs/{job_id}.json with status=indexing

During indexing:
	•	Periodically update job file with chunk_count progress.

On success:
	•	Remove ./repos/{repo_id}/.indexing
	•	Write ./repos/{repo_id}/repo_meta.json with final chunk_count and indexed_at (ISO 8601 UTC).
	•	Update job file: status=complete.

On failure:
	•	Remove ./repos/{repo_id}/.indexing
	•	Update job file: status=failed, error=<message string>.

409 enforcement: /ask, /impact, /repos perform stale-marker cleanup first (A0.3), then check for .indexing on the relevant repo (or any repo for /repos).

A4.1b Overview Detection (SA-1 fix)
Canonical keyword list (case-insensitive substring match on stripped question):
overview, summarize, summary, explain the codebase, what does this repo, high level, high-level, architecture, walkthrough, overall structure
Any match -> overview mode. No other detection logic. No model call. is_overview_query(question: str) -> bool.

A4.1c Retrieval and Diversity (MR-1 fix)
Overview mode:
	•	Query Chroma with n_results=60 (internal).
	•	Deduplicate by (file_path, start_line). Keep first occurrence per pair.
	•	Select up to 20 chunks with hard cap max 2 per file. Never exceed 20.
	•	If fewer than 20 remain after dedup and cap, return however many are available.

Standard mode:
	•	Query Chroma with n_results=12 (internal).
	•	Deduplicate by (file_path, start_line). Keep first occurrence per pair.
	•	Select up to 8 chunks with soft cap max 4 per file.
	•	If 8 cannot be filled: relax cap to 5, then relax cap entirely (no cap).
	•	If still fewer than 8 after full relaxation, return however many are available (minimum 1).
	•	Do not pad with duplicates under any circumstance.

A4.1d Confidence Computation (mechanical — CB-4 fix)
FINAL RULE: confidence is computed from the selected (final) chunk list only.
1. For each selected chunk: sim = 1 - chroma_distance  (valid only with hnsw:space=cosine)
2. avg = mean(all sims in selected list)
3. confidence_score = round(avg, 2)
4. Labels: >= 0.55 = High | >= 0.35 = Medium | < 0.35 = Low
5. Frontend shows warning banner if confidence_label = Low.

A4.1e Evidence Labeling (CB-1 fix)
CRITICAL ORDERING RULE:
Step 1: Finalize chunk list (post-dedup, post-diversity-cap, post-sort).
Step 2: Assign E1..Ek labels in final list order. E1 = first chunk, Ek = last chunk.
Step 3: Build LLM prompt using labeled list. LLM call happens AFTER labeling.
The LLM prompt MUST include all chunk texts with their E-labels.
Claims returned by LLM must only reference E-IDs present in this labeled list.
Violation of this ordering causes evidence ID mismatch. There are no exceptions.

A4.1f LLM Call — Strict JSON Claims (Fallback A)
Prompt hard constraints in system message:
	•	"Use only the provided evidence chunks."
	•	"Every claim must cite at least one evidence ID from E1..Ek."
	•	"Return valid JSON array only: [{\"claim\": \"...\", \"evidence\": [\"E1\", \"E3\"]}]. No other keys. No prose."

Fallback A — failure handling (CB-3 fix):
try:
    raw = llm_response_text
    parsed = json.loads(raw)
    if not isinstance(parsed, list):
        raise ValueError('LLM returned non-list JSON')
    claims = parsed
except (json.JSONDecodeError, ValueError):
    claims = []
    llm_fallback_used = True
This block catches: truncated JSON, syntactically valid but wrong-type JSON, any other parse failure. Backend never raises 500 due to LLM output.

A4.2b Word-Boundary Grep (mechanical)
pattern = re.compile(r"\b" + re.escape(function_name) + r"\b")
	•	Scan all kept source files under ./repos/{repo_id}/.
	•	Collect matching_files set (files containing at least one match).

A4.2c Definition File Detection (MR-4 fix)
Heuristic patterns:
	•	Python: ^\s*def\s+{name}\s*\( and ^\s*class\s+{name}\s*[\(:]
	•	JS/TS: ^\s*function\s+{name}\s*\( and ^\s*(export\s+)?(const|let|var)\s+{name}\s*=\s*(async\s*)?\( and ^\s*(export\s+default\s+)?class\s+{name}\b

Selection algorithm (MR-4 fix):
	•	Among files in matching_files, find those with a definition-pattern match.
	•	Filter out any file whose path contains the substrings 'test', 'mock', or 'stub' (case-insensitive).
	•	Among remaining candidates, find the first line where a definition pattern fires in each file.
	•	Pick the file with the earliest such line number. Tie-break: shortest file path string.
	•	If no candidates remain after step 2 (all are test/mock/stub files), use the candidate with the earliest line number without the path filter.
	•	If no definition-pattern match found at all: definition_file = null.

Result:
	•	files_referencing = matching_files - {definition_file}  (set difference, definition_file may be null)
	•	file_count = len(files_referencing)

A4.2d Mechanical Risk Level
file_count (referencing files)
risk_level
0 or 1
Low
2 or 3
Medium
4 or more
High

Risk is derived from file_count of files_referencing only. LLM never sets or influences risk_level. The LLM risk_level field in its output is informational only and is not used.

A4.2e Grep Context Window (MR-3 fix)
	•	For each referencing file, for first up to 2 grep matches:
start = max(0, match_line - 10)
end = min(len(lines), match_line + 10)
chunk_text = '\n'.join(lines[start:end])
	•	Negative indices are impossible with this clamp. Both bounds are always applied.

A4.2f Grep Finds Nothing
	•	If matching_files is empty: file_count=0, files_referencing=[], risk_level="Low".
	•	message = "No exact word-boundary grep matches found. Showing semantic evidence only."
	•	Still return vector chunks and LLM what_it_does (if available).

A4.2g Evidence Merge and Labeling
Order of operations:
	•	Build grep evidence chunks (context-windowed, bounds-clamped per A4.2e).
	•	Embed function_name with text-embedding-3-small.
	•	Query Chroma for top 6 chunks (no diversity cap on /impact).
	•	Merge: deduplicate by (file_path, start_line, end_line). Keep first occurrence.
	•	Order: grep evidence first, then vector evidence.
	•	Freeze final list. Assign E1..En labels in order (same rule as A4.1e).
	•	Build LLM prompt with labeled list AFTER step 6.

similarity for grep chunks: null. similarity for vector chunks: round(1 - chroma_distance, 4).

A4.2h LLM what_it_does
	•	LLM produces what_it_does as a summary of evidence only.
	•	Fallback A applies (same json.loads + isinstance check). If fails: what_it_does = "", llm_fallback_used = true.
	•	LLM output never alters risk_level or file_count.
