AI CODEBASE GUIDE
Failure Scenarios + Mitigations Spec  ·  Backend
AUTHORITY & SCOPE
Derived exclusively from Combined Backend Master Plan v2 and API Contracts & Schemas Final. No new endpoints or infrastructure. Every failure returns structured JSON matching the canonical ErrorResponse or the degraded-success contract. The backend never produces HTML error pages, blank responses, or unhandled 500s.
HTTP 200 with llm_fallback_used=true is a DEGRADED SUCCESS — not an error. The frontend must handle it gracefully.

Failure Case Specifications

F-01.  ZIP too large — compressed size exceeds 15 MB    HTTP 413
where_it_happens
POST /upload — Step 1: content-length check before any extraction
detection_condition
Uploaded file content-length (or streamed byte count) exceeds 15,728,640 bytes (15 MB).
http_status
413
response_body
{
  "error":   "zip_too_large",
  "message": "Compressed upload size exceeds the 15 MB limit.",
  "repo_id": null,
  "details": { "limit_bytes": 15728640, "received_bytes": <actual> }
}
frontend_render
Show an inline upload error: 'File too large. Maximum compressed size is 15 MB.'
logging
LOG WARN: upload rejected — compressed size <n> bytes exceeds 15 MB limit; no files written to disk.


F-02.  ZIP too large — uncompressed content exceeds 200 MB    HTTP 413
where_it_happens
POST /upload — Step 2: ZipInfo sum check before extraction begins
detection_condition
Sum of ZipInfo.file_size across all entries exceeds 209,715,200 bytes (200 MB); evaluated before any bytes are extracted.
http_status
413
response_body
{
  "error":   "zip_too_large",
  "message": "Uncompressed content size exceeds the 200 MB limit.",
  "repo_id": null,
  "details": { "limit_bytes": 209715200, "declared_bytes": <sum> }
}
frontend_render
Show an inline upload error: 'Repository too large. Maximum uncompressed size is 200 MB.'
logging
LOG WARN: upload rejected — declared uncompressed size <n> bytes exceeds 200 MB limit; no extraction attempted.

F-05.  Stale .indexing marker detected and cleaned up    HTTP 200
where_it_happens
Any of: POST /ask, POST /impact, GET /repos — Step 0: stale-marker cleanup pass (runs before every 409 check)
detection_condition
os.path.getmtime('./repos/{repo_id}/.indexing') returns a value more than 1800 seconds before current time (i.e., marker is > 30 minutes old).
http_status
200
response_body
// This is NOT an error response.
// The stale marker is silently deleted.
// The endpoint then proceeds normally as if no .indexing file existed.
// If repo_meta.json is present -> normal 200 response.
// If repo_meta.json is absent -> 404 repo_not_found (see F-08).
//
// No stale-marker field is included in any response body.
frontend_render
Frontend sees no indication of the stale marker; endpoint responds as if indexing never occurred.
logging
LOG WARN: stale .indexing marker removed — repo_id=<id>, marker_age=<seconds>s, path=./repos/<id>/.indexing.

F-12.  OpenAI embedding API rate limit or timeout mid-indexing    HTTP 200
where_it_happens
Background indexing task — embedder.py: batch embedding call to text-embedding-3-small
detection_condition
openai.RateLimitError, openai.Timeout, httpx.TimeoutException, or equivalent network error raised during any batch embedding call.
http_status
200
response_body
// This failure occurs in a background task.
// /upload already returned 202. The job transitions to failed.
//
// ./jobs/{job_id}.json is updated to:
{
  "job_id":      "<id>",
  "repo_id":     "<id>",
  "status":      "failed",
  "chunk_count": <chunks_completed_before_failure>,
  "error":       "Embedding API error: <exception message>"
}
//
// ./repos/{repo_id}/.indexing is removed.
// ./repos/{repo_id}/repo_meta.json is NOT written.
// Partial Chroma upserts remain but repo is not queryable (no repo_meta.json).
frontend_render
Polling /status/{job_id} returns status='failed' and error message; show 'Indexing failed: Embedding API error. Please retry upload.'
logging
LOG ERROR: embedding batch failed — job_id=<id>, repo_id=<id>, chunks_done=<n>, error=<exception>; .indexing marker removed; repo_meta.json not written.


F-13.  Partial indexing then failure — job marked failed, marker cleaned up    HTTP 200
where_it_happens
Background indexing task — any step after .indexing is created: chunking, embedding, or Chroma upsert
detection_condition
Any unhandled exception or explicit failure condition raised inside the background indexing coroutine after job status has been set to 'indexing'.
http_status
200
response_body
// Background task only. /upload already returned 202.
//
// Cleanup sequence on any indexing failure:
// 1. Catch exception in top-level try/except of background task.
// 2. Remove ./repos/{repo_id}/.indexing  (mandatory — never leave marker orphaned).
// 3. Update ./jobs/{job_id}.json:
{
  "job_id":      "<id>",
  "repo_id":     "<id>",
  "status":      "failed",
  "chunk_count": <last_known_count>,
  "error":       "<exception class>: <message>"
}
// 4. Do NOT write repo_meta.json.
// 5. Partial ./repos/{repo_id}/ directory and partial Chroma data remain.
//    They are inaccessible because repo_meta.json is absent (404 oracle).
//    Operator must manually DELETE /repos/{repo_id} to clean up.
frontend_render
Polling /status shows status='failed' with error string; show 'Indexing failed. Please delete this repository and retry the upload.'
logging
LOG ERROR: indexing task failed — job_id=<id>, repo_id=<id>, error=<exc>, .indexing removed, repo_meta.json not written.


F-14.  Server restart during active indexing — orphaned .indexing marker    HTTP 200
where_it_happens
App startup + next request to POST /ask, POST /impact, or GET /repos that triggers stale-marker cleanup
detection_condition
After restart: ./repos/{repo_id}/.indexing exists with mtime > 1800 seconds ago. The background task that created it is no longer running.
http_status
200
response_body
// On restart:
// - The background indexing task is dead.
// - The job file ./jobs/{job_id}.json still shows status="indexing".
// - ./repos/{repo_id}/.indexing has mtime = time of last server stop.
//
// First request that runs stale-marker cleanup (F-05 rule):
// - Finds .indexing with mtime > 1800s -> deletes it.
// - repo_meta.json is absent (indexing never completed).
// - Request returns 404 repo_not_found (see F-09 or F-10).
//
// Job file is NOT auto-updated to "failed" at restart.
// It remains "indexing" until the job file cleanup rule applies
// (mtime > 86400s -> deleted on next startup).
//
// Pre-indexed demo repo is unaffected: it has repo_meta.json.
frontend_render
After the stale marker is cleaned, /ask or /repos returns normally (200 or 404); no special UI required beyond the standard error rendering.
logging
LOG WARN: orphaned .indexing marker cleaned at stale-marker check — repo_id=<id>, marker_age=<s>s; no repo_meta.json found; repo treated as not-indexed.

  "retrieval_mode":    "standard|overview",
  "confidence_score":  0.58,
  "confidence_label":  "High",
  "claims":            [],
  "chunks":            [ /* full evidence pack, unchanged */ ],
  "llm_fallback_used": true
}
//
// For /impact:
{
  "repo_id":           "<id>",

F-17.  LLM returns invalid JSON (parse failure) — Fallback A    HTTP 200
where_it_happens
POST /ask or POST /impact — json.loads() call on raw LLM response text in llm.py
detection_condition
json.JSONDecodeError raised by json.loads(llm_response_text). Covers: truncated response (token limit hit), embedded prose before/after JSON, malformed escape sequences.
http_status
200
response_body
// Fallback A activates. Same degraded-success shape as F-16.
//
// For /ask: claims=[], llm_fallback_used=true.
// For /impact: what_it_does="", llm_fallback_used=true.
// All other fields (chunks, confidence, risk_level, file_count) are unaffected.
//
// The backend NEVER propagates the raw malformed LLM text to the client.
frontend_render

logging
LOG WARN: LLM JSON parse failed (JSONDecodeError) — endpoint=<ask|impact>, repo_id=<id>; Fallback A activated; raw_length=<n> chars logged at DEBUG level.

frontend_render

LOG WARN: LLM returned non-list JSON type — endpoint=<ask|impact>, repo_id=<id>, actual_type=<type>; Fallback A activated.

http_status
200
response_body
// VALID SUCCESS (200). Fallback rule applies:
// Re-run definition candidate selection without test/mock/stub filter.
// Pick the file with the earliest definition-pattern line number.
// Tie-break: shortest path. This becomes definition_file.
// files_referencing = matching_files - {definition_file}.
//
// Response shape is identical to the normal /impact 200 response.
// definition_file (a test file) is still excluded from files_referencing.
// This may slightly undercount risk — acceptable per spec.
{
  "repo_id":           "demo_repo",
  "function_name":     "verify_credentials",
  "risk_level":        "Low",
  "file_count":        1,
  "files_referencing": ["src/routes.py"],
  "what_it_does":      "...",
  "message":           null,
  "chunks":            [ /* ... */ ],
  "llm_fallback_used": false
}
frontend_render
Render impact results normally; no special UI required — this fallback is fully transparent to the frontend.
logging
LOG DEBUG: /impact definition detection — all candidates were test/mock/stub paths; fallback to unfiltered selection; definition_file=<path>; repo_id=<id>.

Non-Negotiable Invariants

	•	1. Every error response uses the canonical ErrorResponse shape. No deviations.
	•	2. The backend never returns HTML, a blank body, or an unhandled exception trace to the client.
	•	3. Fallback A (F-16, F-17, F-18) always returns HTTP 200 with llm_fallback_used=true. It never returns 500.
	•	4. Stale .indexing marker cleanup (F-05) runs BEFORE every 409 check. This is mandatory, not optional.
	•	5. repo_meta.json is the sole existence oracle for every repo. No repo_meta.json = 404. Always.
	•	6. The job file ./jobs/{job_id}.json is ALWAYS updated to status=failed and .indexing ALWAYS removed when any indexing failure occurs (F-12, F-13).
	•	7. similarity=null for all grep-sourced chunks. Never 0. Never omitted. (F-19, F-20, F-21 all preserve this.)
	•	8. /health and /status/{job_id} never return 409 under any condition.
	•	9. Evidence E-labels are assigned after the final chunk list is frozen and before the LLM call, in all code paths including degraded/fallback paths.
	•	10. No failure case introduces a new endpoint, new infrastructure component, or new external dependency.
