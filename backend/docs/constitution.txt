SECTION 1 — System Architecture & Execution Flow

1.1 Project Identity
The AI Codebase Guide is a two-tab web application that performs retrieval-augmented code analysis. It is not a chatbot. It is not a GPT wrapper. Every answer surfaces the exact code chunks it used, every citation is clickable, and every impact score is computed mechanically from grep results — not inferred by a model.

1.8 Data Flow Summary
Ingestion flow:
	•	POST /upload → validate ZIP → create job file + .indexing marker → return 202 immediately
	•	Background task: filter files → chunk (100 lines, 20-line overlap) → embed (batches of 64) → upsert Chroma
	•	On success: remove .indexing, write repo_meta.json, set job=complete
	•	On failure: remove .indexing, set job=failed with error message, do NOT write repo_meta.json

Ask flow:
	•	Guard: stale cleanup → 409 check → 404 check
	•	Detect mode (keyword match) → retrieve (12 or 60 internal) → dedup → diversity cap → freeze list
	•	Assign E1..Ek labels → build LLM prompt → call LLM → Fallback A → return AskResponse

Impact flow:
	•	Guard: stale cleanup → 409 check → 404 check
	•	Word-boundary grep → definition detection → build grep chunks (clamped context)
	•	Embed function_name → query Chroma top-6 → merge + dedup → freeze list
	•	Assign E1..En labels → build LLM prompt → call LLM → Fallback A → return ImpactResponse

2.3  POST /upload
Request — multipart/form-data
# Field name: file
# Content-Type: multipart/form-data
async def upload(file: UploadFile = File(...)): ...

ZIP Validation Sequence — must execute in this exact order
1. Reject if content-length > 15,728,640 bytes (15 MB compressed) → 413 zip_too_large.
2. Open ZIP. Sum ZipInfo.file_size across all entries. If sum > 209,715,200 bytes (200 MB) → 413 zip_too_large.
3. Validate each entry: deny absolute paths, deny '..' segments, deny drive-letter prefixes.

5. Filter files (see Section 4). Move filtered files to ./repos/{repo_id}/.
Response returns immediately (202). All further work runs in background.

SECTION 3 — Guard Order & State Transitions

3.1 Universal Guard Protocol
Every guarded endpoint must execute the following steps in this exact order. Violation of this order is a defect.

Step
Action
0 — Stale cleanup
For each relevant .indexing file (repo-specific for /ask and /impact; all repos for /repos): if mtime > 1800 seconds ago, delete the file immediately. This step runs unconditionally before any 409 check.
1 — 409 check
After cleanup, check whether the (now-current) .indexing file exists. For /ask and /impact: check ./repos/{repo_id}/.indexing. For /repos: check any ./repos/*/.indexing. If present: return 409.
2 — 404 check
/ask and /impact only: check ./repos/{repo_id}/repo_meta.json. If absent: return 404. /repos: not applicable (returns list of all repos with repo_meta.json). DELETE /repos/{repo_id}: check repo_meta.json; 404 if absent.
3 — Proceed
All guards passed. Execute the endpoint's primary logic.

3.2 Endpoints Exempt from Guards
Endpoint
Exemption
GET /health
Fully exempt. No guards. No 409. No 404. Always returns 200.
GET /status/{job_id}
Fully exempt from indexing guard. Never returns 409. Returns 404 only if job file is absent.
DELETE /repos/{repo_id}
Exempt from 409 guard. No stale cleanup required. 404 check on repo_meta.json still applies.

3.3 Indexing State Machine
State
Conditions
Next States
not_indexed
./repos/{repo_id}/ absent OR repo_meta.json absent
→ indexing (via POST /upload)
indexing
./repos/{repo_id}/.indexing exists AND mtime <= 1800s
→ complete (on success) | → failed (on error) | → stale (on server crash)
stale
./repos/{repo_id}/.indexing exists AND mtime > 1800s
→ not_indexed (stale cleanup removes marker; no repo_meta.json → 404)
complete
repo_meta.json exists AND no .indexing file
→ not_indexed (via DELETE) | → indexing (via new POST /upload for same repo_id)
failed
job file status='failed', .indexing absent, repo_meta.json absent
→ not_indexed (operator runs DELETE to clean partial data) | → indexing (via new upload)

State transition enforcement:
complete → indexing (re-upload): must DELETE /repos/{repo_id} first. New upload creates new job_id.
stale state self-heals: first guarded request that runs stale cleanup removes the marker. No explicit recovery endpoint needed.
failed state is terminal: operator must call DELETE /repos/{repo_id} before re-uploading. Partial Chroma data and partial ./repos/{repo_id}/ directory remain but are inaccessible (no repo_meta.json).

	•	Split each filtered file into chunks of 100 lines with 20-line overlap.
	•	Chunk metadata fields: repo_id, file_path (relative to repo root, no leading slash), start_line (0-indexed), end_line (0-indexed, inclusive), chunk_index (0..n-1), sha1(chunk_text)[:8].
	•	Chunk ID: f"{file_path}:{chunk_index}:{sha1[:8]}"

SECTION 5 — Vector Store & Embedding Rules

5.1 Chroma Collection Creation — Mandatory Configuration
# This exact call is required for every collection. No exceptions.
collection = client.get_or_create_collection(
    name=f"repo_{repo_id}",
    metadata={"hnsw:space": "cosine"}   # REQUIRED: enables sim = 1-d formula
)

# Naming rule: always f"repo_{repo_id}"
# Demo repo: collection = repo_demo_repo (repo_id = demo_repo)

hnsw:space=cosine is not optional. Without it, ChromaDB defaults to L2 distance. L2 distances are unbounded and can exceed 2.0. The formula sim = 1 - d produces negative values with L2, breaking confidence computation. This is a hard correctness requirement.
Conflict resolution: API Contracts and Combined Backend Master Plan v2 both specify cosine. Rev 2 did not specify distance function. The stricter (explicit) specification prevails.

5.4 Confidence Computation — Mechanical, Always
Formula (applies identically to standard and overview mode):
1. For each selected chunk i: sim_i = 1 - chroma_cosine_distance_i
   This is valid ONLY when hnsw:space=cosine is set. Result is in [0.0, 1.0].
2. confidence_score = round(mean([sim_1, sim_2, ... sim_k]), 2)
3. confidence_label thresholds:
   >= 0.55  →  High
   >= 0.35  →  Medium
   <  0.35  →  Low  [frontend MUST display warning banner]
Confidence is computed from the SELECTED chunk list only. LLM never reports or influences confidence.

SECTION 6 — LLM Layer & Fallback A Enforcement

6.1 Overview Detection (SA-1 fix) — POST /ask only
Detection method: case-insensitive substring match on stripped question string.
No model call. No extra latency. No separate classification step.
Canonical keyword list (any single match triggers overview mode):
  overview  |  summarize  |  summary  |  explain the codebase  |  what does this repo
  high level  |  high-level  |  architecture  |  walkthrough  |  overall structure
is_overview_query(question: str) -> bool

6.2 Evidence Labeling — Mandatory Ordering
CRITICAL: Violation of this ordering produces evidence ID mismatch and breaks all citations.
Step 1: Finalize the chunk list. Apply: dedup by (file_path, start_line) → diversity cap → sort.
Step 2: Assign E1..Ek labels. E1 = index 0. Ek = last index. Labels are assigned in this list order only.
Step 3: Build the LLM prompt. Embed all labeled chunk texts into the system/user message.
Step 4: Call the LLM. The LLM MUST receive all E-IDs and chunk texts in the prompt.
The LLM call MUST occur AFTER labeling. No exceptions. No early LLM calls.
This rule applies identically to /ask and /impact.

6.3 LLM Prompt Hard Constraints (System Message)
# These exact constraints must appear in the LLM system message:
"Use only the provided evidence chunks."
"Every claim must cite at least one evidence ID from E1..Ek."
"Return valid JSON array only: [{\"claim\": \"...\", \"evidence\": [\"E1\", \"E3\"]}].
 No other keys. No prose outside the JSON array."

6.4 Fallback A — Complete Specification (CB-3 fix)
try:
    raw    = llm_response_text
    parsed = json.loads(raw)
    if not isinstance(parsed, list):
        raise ValueError("LLM returned non-list JSON")
    claims = parsed
    llm_fallback_used = False
except (json.JSONDecodeError, ValueError):
    claims            = []
    llm_fallback_used = True

# Fallback A catches ALL of the following:
# - Network failure / timeout before any response received
# - Non-200 HTTP response from OpenAI API
# - Truncated response (token limit hit mid-array) -> JSONDecodeError
# - Valid JSON but not a list (e.g. {"answer": "..."}) -> ValueError
# - Any other exception in the LLM call path

# When Fallback A fires:
# /ask:    claims=[], llm_fallback_used=True, chunks and confidence UNCHANGED
# /impact: what_it_does='', llm_fallback_used=True, chunks and risk UNCHANGED

# Fallback A ALWAYS returns HTTP 200. NEVER returns 500.
# The raw malformed LLM text is NEVER propagated to the client.

7.1 Word-Boundary Grep

7.2 Grep Context Window — Bounds-Clamped (MR-3 fix)
# For each file in referencing_files, for first up to 2 grep matches:
for match_line in first_two_match_lines(file):
    start      = max(0, match_line - 10)       # ALWAYS clamp lower bound
    end        = min(len(lines), match_line + 10)  # ALWAYS clamp upper bound
    chunk_text = '\n'.join(lines[start:end])

# Negative slice indices are impossible with this clamp.
# Both bounds are mandatory. Neither may be omitted.

7.3 Definition File Detection Algorithm (MR-4 fix)
Heuristic patterns:
Python: ^\s*def\s+{name}\s*\(   and   ^\s*class\s+{name}\s*[\(:]
JS/TS:  ^\s*function\s+{name}\s*\(   and   ^\s*(export\s+)?(const|let|var)\s+{name}\s*=\s*(async\s*)?\(   and   ^\s*(export\s+default\s+)?class\s+{name}\b

Selection algorithm (execute in this order):
	•	Among files in matching_files, find those containing a definition-pattern match.
	•	Filter out any file whose path contains 'test', 'mock', or 'stub' (case-insensitive substring match).
	•	Among remaining candidates: for each file, find the earliest line where a definition pattern fires.
	•	Pick the file with the smallest such line number. Tie-break: shortest file path string (lexicographic).
	•	If no candidates remain after step 2 (all were test/mock/stub): re-run steps 3-4 WITHOUT the path filter.
	•	If no definition pattern found in any file in matching_files: definition_file = null.

Result:
files_referencing = matching_files − {definition_file}    (set difference; definition_file may be null)
file_count = len(files_referencing)
definition_file is an internal implementation detail. It is NEVER exposed in any response body.

Risk is derived solely from file_count of files_referencing. The LLM never sets, suggests, or influences risk_level. If the LLM output contains a risk_level field: discard it. The mechanically computed value is always used.

SECTION 10 — Non-Negotiable Invariants (Complete Table)

Every invariant in this table is absolute. No invariant may be weakened, omitted, or conditioned on runtime state. These rules apply without exception across all code paths, including fallback and degraded paths.

Invariant #
Rule
I-01
Every error response from every endpoint uses the canonical ErrorResponse shape. No endpoint may return HTML, a blank body, or an unhandled exception trace.
I-02
The backend never returns HTTP 500 due to LLM output. LLM failures, JSON parse failures, and wrong-type JSON always trigger Fallback A (HTTP 200, llm_fallback_used=true).
I-03
Stale .indexing marker cleanup (mtime > 1800s → delete) MUST run before every 409 check. This is mandatory, not optional, not best-effort.
I-04
repo_meta.json is the sole existence oracle. repo_meta.json present = repo exists. repo_meta.json absent = 404. No other signal overrides this.

I-06
similarity MUST be null (JSON null) for all grep-sourced EvidenceChunk objects. Never 0. Never omitted.
I-07
GET /health and GET /status/{job_id} MUST never return 409 under any condition.
I-08
Evidence E-labels (E1..Ek) MUST be assigned after the final chunk list is fully frozen (post-dedup, post-sort) and BEFORE the LLM call. This order is absolute.
I-09
hnsw:space=cosine MUST be set on every get_or_create_collection() call. Without it, sim=1-d produces invalid values.

The mode field in POST /ask requests is accepted but never read. Backend always auto-detects overview vs standard via keyword matching.
I-11

I-13
Chroma collection names MUST always equal f"repo_{repo_id}". Demo repo collection MUST be repo_demo_repo. No deviations.
I-14
The grep context window MUST apply both bounds: start=max(0, match_line-10) AND end=min(len(lines), match_line+10). Both clamps are mandatory.
I-15
The definition_file field is an internal implementation detail. It MUST NEVER appear in any response body sent to the client.
I-16
